# 公開・配信方針

## 基本方針：Webサイト + GitHub の二層構造

本当の利用者である非IT職の実務者に、GitHubのリポジトリを読ませる体験にはしない。一般の利用者にはWebサイトで、技術者や改善に参加したい人にはGitHubで届ける。

| 窓口 | 誰のためか | 役割 |
|---|---|---|
| Webサイト（表） | 一般の実務者 | 業務から探す、カードで判断する、プロンプトをコピーして使う |
| GitHub（裏） | 技術者・改善に参加したい人 | 設計思想、プロンプトの版、評価結果、Issue・Pull Requestによる改善 |
| note・SNS（入口） | まだ存在を知らない人 | 問題提起とストーリーで関心を持ってもらい、サイトかGitHubへ誘導する |

## 正本はGitHubリポジトリ

- Recipeの内容（本文・プロンプト・評価）は、このリポジトリを唯一の正本とする
- Webサイトはリポジトリから生成し、サイト側でRecipeの内容を直接編集しない
- そのため、Recipeはメタデータとファイル構成を [recipe-spec.md](recipe-spec.md) どおりに保つ。サイトは `page.md` のフロントマターからカードと一覧を、`page.md` の本文からRecipeのページ（「なぜうまくいくの？」を含む）を、`prompts/` からコピー用プロンプトを、`categories.yml` から業務カテゴリの表示を、`guides/` からサイト共通ページを作る。`README.md` はサイトに表示せず、GitHubへのリンクだけを置く
- 利用者がGitHubを開かなくても使えるようにする。サイトのRecipeページからGitHubへのリンクは、「設計と評価を見る（技術者向け）」のように目立たない形で置く

## Webサイト

### URL

`tariki-code.tokyo` のサブドメインに新しいサイトとして置く（例：`ai-work-recipes.tariki-code.tokyo`）。既存サイトとは分けて運用し、相互にリンクする。

### ホスティング

静的サイトとして生成し、**Cloudflare Pages** で配信する。静的サイト生成ツールは **Astro** を使い、`site/` に置く（ビルドと設定は [../site/README.md](../site/README.md)）。Astro はオープンソース（MITライセンス）で、出力は静的なHTMLになるため、サーバーの費用はかからない。

- `tariki-code.tokyo` のDNSはNetlifyで管理している。DNSは移さず、Netlify DNSにサブドメインのCNAMEレコード（`<project>.pages.dev` 宛て）を追加する。Cloudflare Workersの独自ドメイン機能はDNSをCloudflareへ移す必要があるため使わない
- 同じサブドメインをNetlifyのサイトに割り当てない。ドメインにCAAレコードがある場合は、Cloudflareが証明書を発行できるか確認する
- GitHubリポジトリと連携し、pushで自動デプロイする。ブランチごとのプレビューURL（`*.pages.dev`）は初期状態で誰でも見られるため、公開前のRecipeを見せたくない場合はCloudflare Accessで制限する
- 無料プランで運用する。静的サイトの配信は無制限、ビルドは月500回まで（2026年10月時点。変更があり得るため、公開時に公式ドキュメントで確認する）
- Cloudflare Access の無料枠（50ユーザー）は、ログインしてプレビューを見る人の数で数える。公開サイトにはAccessをかけないため、利用者数には関係しない

### 利用者のネットワーク環境

自治体や企業のネットワークでは、新しいドメインや分類されていないサイト、`*.pages.dev` が遮断されることがある。

- 利用者には独自サブドメインのURLだけを案内する
- 外部CDNや外部スクリプトに頼らず、サイトの中で完結させる。フォントもサイトに含めて配信する
- 例外として、アクセス解析（Google Analytics）の gtag.js だけは外部から読み込む。非同期で読み込み、遮断されてもサイトの動きには影響しない（計測されないだけ）。設定は [../site/README.md](../site/README.md) の「Google Analytics」
- 公開後、実際の自治体・企業のネットワークから開けるかを確認する

### フィードバック

静的サイトでは利用者の声を受け取れない。利用者にGitHubのIssueを書いてもらうことは想定せず、βの段階ではフォーム（Googleフォームなど）へのリンクを置く。利用者からの新しいレシピの要望も、同じフォームで受け付ける。質問の内容、フォームの設定、サイトとの連携は [feedback-form.md](feedback-form.md) を参照する。

### 画面の考え方

画面の詳しい基準は [site-design.md](site-design.md) とモック [mock/site-mock.html](mock/site-mock.html) を参照する。以下は最初の構想時のイメージ。

```text
AI業務レシピ

🔍 業務から探す
会議｜文章作成｜要約｜調査｜企画｜情報整理

文字起こしから議事録を作る
⏱ 約3分　★☆☆　GPT-4.1で動作確認

使い方
① 文字起こしを貼る　　　　［STEP 1のプロンプトをコピー］
② 必要なら質問に答える
③ 議事録に仕上げる　　　　［STEP 3のプロンプトをコピー］

▼ なぜこのプロンプトでうまくいくの？

技術者の方へ：設計・評価・改訂履歴を見る（GitHub）
```

- 一覧とRecipeの冒頭には、カード（難易度・作業時間・最低動作モデル・操作数・AI知識）を出す
- 使い方とコピーボタンを最優先で見せ、「なぜうまくいくの？」は折りたたんで下に置く

## note・SNS

本体ではなく入口として使う。例えば次のような問題提起の記事を書き、議事録Recipeを紹介する。記事の材料には、各Recipeの `README.md`（設計目標、仕事の分解、設計思想）が使える。

> 「プロンプトを勉強しない人」のためのプロンプトを作りたい

記事からは「使いたい人はサイトへ」「中身を検証したい人はGitHubへ」と誘導する。

## 公開の段階

1. GitHubでRecipeの仕様と最初のRecipeを整える（現在）
2. 基本の5本を同じ形式で揃え、Webサイトを「AI業務レシピ β」として公開する
3. note・SNSで紹介し、地域コミュニティでの検証結果を反映していく
