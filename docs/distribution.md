# 公開・配信方針

## 基本方針：Webサイト + GitHub の二層構造

本当の利用者である非IT職の実務者に、GitHubのリポジトリを読ませる体験にはしない。一般の利用者にはWebサイトで、技術者や改善に参加したい人にはGitHubで届ける。

| 窓口 | 誰のためか | 役割 |
|---|---|---|
| Webサイト（表） | 一般の実務者 | 業務から探す、カードで判断する、プロンプトをコピーして使う |
| GitHub（裏） | 技術者・改善に参加したい人 | 設計思想、プロンプトの版、評価結果、Issue・Pull Requestによる改善 |
| note・SNS（入口） | まだ存在を知らない人 | 問題提起とストーリーで関心を持ってもらい、サイトかGitHubへ誘導する |

## 正本はGitHubリポジトリ

- Recipeの内容（本文・プロンプト・評価）は、このリポジトリを唯一の正本とする
- Webサイトはリポジトリから生成し、サイト側でRecipeの内容を直接編集しない
- そのため、Recipeはメタデータとファイル構成を [recipe-spec.md](recipe-spec.md) どおりに保つ。サイトは `page.md` のフロントマターからカードと一覧を、`page.md` の本文からRecipeのページを、`prompts/` からコピー用プロンプトを、`README.md` から「なぜこのプロンプトでうまくいくの？」の解説を作る
- 利用者がGitHubを開かなくても使えるようにする。サイトのRecipeページからGitHubへのリンクは、「設計と評価を見る（技術者向け）」のように目立たない形で置く

## Webサイト

### URL

`tariki-code.tokyo` のサブドメインに新しいサイトとして置く（例：`ai-work-recipes.tariki-code.tokyo`）。既存サイトとは分けて運用し、相互にリンクする。

### ホスティング

静的サイトとして生成し、Cloudflareでの配信を第一候補とする（Vercelも比較対象として残す）。技術選定はフェーズ2の開始時に行い、次の観点で決める。

- `tariki-code.tokyo` のDNS管理との相性（サブドメインの設定が簡単か）
- リポジトリへのpushで自動デプロイできるか
- 無料枠で運用できるか
- 将来、検索やタグ絞り込みを追加しやすいか

### 画面の考え方

```text
AI業務レシピ

🔍 業務から探す
会議｜文章作成｜要約｜調査｜企画｜情報整理

文字起こしから議事録を作る
⏱ 約3分　★☆☆　GPT-4.1で動作確認

使い方
① 文字起こしを貼る　　　　［STEP 1のプロンプトをコピー］
② 必要なら質問に答える
③ 議事録に仕上げる　　　　［STEP 3のプロンプトをコピー］

▼ なぜこのプロンプトでうまくいくの？
```

- 一覧とRecipeの冒頭には、カード（難易度・作業時間・最低動作モデル・操作数・AI知識）を出す
- 使い方とコピーボタンを最優先で見せ、設計理由（`README.md` から）は折りたたむか下に置く

## note・SNS

本体ではなく入口として使う。例えば次のような問題提起の記事を書き、議事録Recipeを紹介する。記事の材料には、各Recipeの `README.md`（設計目標、仕事の分解、設計思想）が使える。

> 「プロンプトを勉強しない人」のためのプロンプトを作りたい

記事からは「使いたい人はサイトへ」「中身を検証したい人はGitHubへ」と誘導する。
