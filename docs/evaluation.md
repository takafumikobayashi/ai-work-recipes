# 評価方針

Recipeは、出力が流暢かどうかだけでなく、実務で安全に使えるかを評価する。

## 基本評価項目

| 項目 | 確認すること |
|---|---|
| 正確さ | 入力にない事実を作っていないか、重要な内容を取り違えていないか |
| 網羅性 | 必要な情報やアクションを落としていないか |
| 根拠追跡性 | 元資料や発言に戻って確認できるか |
| 構造・形式 | 指定した見出し、表、項目の形になっているか |
| 編集負担 | 人間が修正・確認する時間と量が許容範囲か |
| 操作のしやすさ | 初見の利用者が手順を迷わず終えられるか、所要時間がカードの表示どおりか |
| 質問品質 | 本当に必要なことだけを、答えやすい形で質問しているか |
| 再現性 | 同じ条件で大きく品質がぶれないか |
| 制約耐性 | 想定した最低動作モデル・入力条件で使えるか。1回に送れる文字数に上限がある場合に、分けて送っても品質が保てるか |
| 安全性 | 機密情報や不確かな内容を不用意に出していないか |

## 3段階の判定

各項目を次の3段階で記録する。

- **2：合格** — 実務利用の前提を満たす
- **1：条件付き** — 人間の確認や追加手順があれば使える
- **0：不合格** — 目的に対して危険、または作業負担が大きすぎる

「2が多い」だけで公開を決めず、正確さ・安全性・根拠追跡性に0がないことを最低条件とする。1が残る項目は、Recipe本文に確認方法と制約を記載する。

## テストセット

最初から大量のデータを必要としない。Recipeごとに、次のような小さなテストセットを作る。

1. **標準例**：想定する通常の入力
2. **短い例**：入力が少ない場合
3. **長い例**：情報量が多く、重要事項が分散している場合
4. **ノイズを含む例**：誤字、話者の混同、重複、脱線がある場合
5. **曖昧な例**：人間の判断や確認が必要な場合
6. **対立する例**：意見や情報が食い違っている場合
7. **途中で変わる例**：前半の内容が後半で訂正・変更される場合
8. **危険な例**：個人情報、機密、未確認情報を含む場合

すべての類型を毎回そろえる必要はない。その仕事で失敗しやすい類型を優先する。

## 業務固有の評価指標

上の基本評価項目に加えて、各Recipeの `README.md` に、その仕事に固有の指標を定義する（議事録なら「決定事項精度」「ToDo精度」「持ち越し精度」など）。判断基準（定義した分類）ごとに、正しく分類できたかを測る指標を置くとよい。

実データを使う場合は、許可・匿名化・保存場所を確認する。公開用のテストセットは、再現可能なダミーデータを優先する。

## モデル比較

モデルを比較するときは、同じ入力、同じプロンプト、同じ評価項目で確認する。モデル名だけで優劣を決めず、次を記録する。

- モデル名と確認日
- 入力の長さ・形式
- 使用したプロンプトの版
- 成功した点と失敗した点
- 人間の修正にかかった時間

最低動作モデルは「完璧な品質が出るモデル」ではなく、「確認手順を含めればRecipeとして成立する最小条件」と定義する。

Recipeには、結果を次の形式の表で載せる。

| モデル | 動作確認 | 評価 | 確認日 |
|---|---|---|---|
| GPT-4.1 | ✓ | 基準 | YYYY-MM-DD |
| （他のモデル） | 未検証 | — | — |

評価は「基準」（最低動作モデル）、「良好」、「条件付き」（詳細モードや追加確認が必要）、「不可」のいずれかで記す。

### 比較の基準

手順を分けた効果を確かめるため、少なくとも一度は、同じ入力で「一発の短い指示」（例：「この文字起こしから議事録を作成してください」）と比べる。

通常手順で正確さ・安全性・根拠追跡性に0が出るモデルがある場合は、処理を複数のプロンプトに分けた「詳細モード」の追加を検討する。

## 公開前チェック

- 標準例と少なくとも1つの失敗しやすい例を試した
- 重要な誤りが出た場合の確認方法を書いた
- 最低動作モデルと確認日を書いた
- 所要時間を実測し、カードの表示を更新した
- 入力してはいけない情報を書いた
- 人間が最終判断する箇所を明示した
- 評価結果をRecipe本文または付属資料に残した
