# プロンプト設計パターン

Recipeのプロンプトを書くときに使う共通のパターン集。各Recipeの `README.md`（設計と検証）では、ここのパターン番号を使って「どのパターンを、どう使っているか」を示す。

## 前提となる考え方

> **AI側では厳密に、人間側では簡単に。**

複雑さは利用者ではなくプロンプト側に持たせる。利用者に見える操作は「貼る」「選ぶ」「答える」だけにし、プロンプトの内側で処理を分け、判断基準を渡し、確認させる。

これらのパターンは、GPT-4.1のように「期待する動作を暗黙に推測させるより、具体的・明示的に指示した方がよく従う」モデルを最低基準として想定している。新しいモデルでも害にはならず、品質の安定につながる。

## パターン一覧

| 番号 | パターン | 防ぎたい失敗 |
|---|---|---|
| P1 | 処理の順序を固定する | 処理の抜け、途中の手順の飛ばし |
| P2 | 分類は名前ではなく定義と例で渡す | 意見と決定、事実と推測などの混同 |
| P3 | 禁止事項は典型的な失敗として具体的に書く | 推測による補完、勝手な修正 |
| P4 | 分からないことの書き方を決める | 空欄、もっともらしい推測で埋めること |
| P5 | 出力フォーマットを固定する | 形式の揺れ、項目の欠落 |
| P6 | 中間出力を次のステップの入力にする | 事実認定と文章作成が混ざること |
| P7 | 必要なときだけ質問する | 推測による誤り、または質問攻めによる負担 |
| P8 | 何を確認するかを指定してセルフチェックさせる | 「確認しました」だけの形だけの確認 |
| P9 | 入力の区切りを明示し、入力の後で念押しする | 長い入力の後で指示を忘れること |

---

## P1 処理の順序を固定する

「必ず次の順番で処理してください」と書き、番号付きの見出しで処理を並べる。典型的な順序は次のとおり。

```text
抽出 → 判定 → 整理（構造化） → 確認
```

一度に多くを求めず、各段階でやることを一つにする。順序を固定すると、どの段階で失敗したかも切り分けやすくなる。

## P2 分類は名前ではなく定義と例で渡す

「決定事項」「ToDo」のように名前だけを渡すと、モデルごとに解釈が揺れる。各分類に一行の定義を付け、必要なら「含めないもの」も書く。

```text
【決定事項】
会議として明確に合意・確定したこと。
単なる意見、提案、検討案は含めません。
```

設計段階では、紛らわしい発言の例と正しい分類を並べた表を各Recipeの `README.md` に残す。その仕事の品質を左右する区別は何かを最初に洗い出すことが、Recipe設計の中心になる。

## P3 禁止事項は典型的な失敗として具体的に書く

「推測しないでください」だけでは足りない。その仕事で実際に起きやすい失敗を、そのまま禁止事項にする。

```text
- 文脈だけを根拠とした担当者・期限の確定
- 提案を決定事項に変更すること
- 不明な固有名詞を勝手に修正すること
```

禁止事項の候補は、テストで出た失敗から追加していく。

## P4 分からないことの書き方を決める

確認できない項目を空欄にさせると、モデルはもっともらしい値で埋めやすい。分からないときの書き方を決めておく。

| 書き方 | 使う場面 |
|---|---|
| 不明 | 中間出力で、入力から確認できない |
| 要確認 | 完成版で、人間の確認が必要なまま残っている |
| なし | 該当する項目が存在しない |

## P5 出力フォーマットを固定する

見出し・箇条書き・表の形をプロンプト内に書き、「以下の形式で必ず整理してください」と指定する。項目数が変わるもの（議題など）は「数に応じて増減してください」と添える。

## P6 中間出力を次のステップの入力にする

最初のステップでは完成品を作らせず、事実を決まった「箱」に整理させる。次のステップでは「元の資料を解釈し直すのではなく、整理した情報と私の回答を主な根拠として」完成品を作らせる。

```text
生の入力 → 構造化された事実 → 必要なら人間が補完 → 完成品
```

事実認定と文章作成を分離することで、各ステップでAIに求める仕事が単純になり、きれいな文章の中に推測が紛れ込むことを防げる。中間出力は、人間が読んで誤りに気づける形にもなる。

## P7 必要なときだけ質問する

人間への確認は精度を上げるが、質問が多いと利用者の作業時間が増える。次の基準で質問を絞る。

| 状況 | 処理 |
|---|---|
| AIだけで判断できる | AIが処理する |
| AIでは判断できず、成果物にとって重要 | 人間に質問する |
| 不明だが成果物への影響が小さい | 質問せずに進める |

プロンプトでは次を指定する。

- 質問してよい場合の具体例（例：決定か提案か判断できない、重要な担当者が分からない）
- 「不要な質問を大量にすること」の禁止
- 短く答えられる形で質問すること。候補が絞れる場合は選択肢を添えること
- 質問がない場合の決まった文言（例：「重要な確認事項はありません」）

利用者には「分からない場合は『不明です。そのまま進めてください』でよい」と伝え、答えられないことを負担にしない。

## P8 何を確認するかを指定してセルフチェックさせる

「よく確認してください」ではなく、その仕事で典型的な失敗を3〜5個挙げて確認させる。確認作業そのものを出力させるかどうかは、利用者が読む量とのバランスで決める。基本は「確認後の完成版だけを出力」とし、残った不明点は「要確認事項」として成果物に含める。

## P9 入力の区切りを明示し、入力の後で念押しする

貼り付ける場所を、誰が見ても分かる記号で囲む。

```text
↓↓↓ ここから文字起こし ↓↓↓

【ここに文字起こしを貼り付けてください】

↑↑↑ 文字起こしはここまで ↑↑↑
```

長い入力の後では、最初に書いた指示が効きにくくなる。入力の後に、最も重要な原則を短く繰り返す。

## 新しいRecipeでの使い方

1. その仕事を、AIが一度に求められている小さな仕事に分解する（`README.md` の「この仕事の分解」）
2. 品質を左右する区別を洗い出し、定義と例を作る（P2）
3. 中間フォーマットを決める（P5・P6）
4. 人間に質問すべき場面を決める（P7）
5. 典型的な失敗を、禁止事項とセルフチェックに書く（P3・P8）
6. テストで出た失敗を、パターンに沿ってプロンプトへ反映する

テストで繰り返し効果が確かめられた新しい工夫は、パターンとしてこの文書に追加する。
