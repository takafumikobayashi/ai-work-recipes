# Recipe共通仕様

## 目的

利用者と技術者が、それぞれ自分に必要な情報だけを読めるようにする。

- **利用者**（プロンプトを使う人）は、Webサイトだけを見る。GitHubを開くことは想定しない
- **技術者・改善に参加したい人**は、GitHubで設計・評価・改訂履歴まで追える

利用者向けの文章もリポジトリに置くが、それはサイトを生成するための素材であり、GitHub上で利用者に読ませるためのものではない。

新しいRecipeは、[../recipes/template/](../recipes/template/) をディレクトリごと `recipes/<category>/<name>/` に複製して作成する。

## ファイル構成

```text
recipes/
  meeting/                         # 業務カテゴリ（例：meeting、reading）
    minutes-from-transcript/       # Recipe（フォルダ名がサイトのURLになる）
      page.md                      # 利用者向け：サイト表示の素材（カード・使い方・注意・最後の確認）
      prompts/
        step1-<動作>.txt           # 利用者向け：コピーボタンの中身（プロンプト本文のみ）
        step3-<動作>.txt
      README.md                    # 技術者向け：設計と検証（GitHubでフォルダを開くと最初に表示される）
  categories.yml                   # 業務カテゴリの一覧（表示名と並び順）
guides/                            # 利用者向け：サイト共通ページの素材（はじめての方へ、など）
      evals/                       # 技術者向け：テストセットと評価記録（作成時に追加）
```

| ファイル | 読む人 | 読む場所 | 文体 |
|---|---|---|---|
| `page.md` | 利用者 | Webサイト | です・ます調。構想の見本くらい短く |
| `prompts/*.txt` | 利用者 | Webサイト（コピーボタン） | プロンプト本文のみ |
| `README.md` | 技術者・改善したい人 | GitHub | である調 |
| `evals/` | 技術者・改善したい人 | GitHub | — |

- フォルダは `recipes/<category>/<name>/` とする。フォルダの場所はサイトのURL（例：`/meeting/minutes-from-transcript/`）になるため、公開後は原則として変えない
- `category` は [../recipes/categories.yml](../recipes/categories.yml) から選ぶ。増やすときは既存のカテゴリと重ならないか確認し、`categories.yml` に表示名を追加する
- `name` は英小文字とハイフンで、何から何を作るかが分かる名前にする
- プロンプトは `page.md` に埋め込まず、`prompts/` 配下に **プロンプト本文だけ** を置く。`page.md` からはリンクし、サイトではそのリンクをプロンプトとコピーボタンに置き換える
- ファイル名の番号は、利用者の操作ステップに合わせる。人が答えるだけのステップ（STEP 2）にはプロンプトファイルを作らない

## 基本の操作の型

Recipeは原則として、次の3ステップで構成する。

```text
STEP 1　貼る　　　　　：プロンプトと資料を貼る。AIは抽出・判定・整理を行い、必要な場合だけ質問する
STEP 2　必要なら答える：質問に短く答える。質問がなければ飛ばす
STEP 3　仕上げる　　　：完成版用のプロンプトを送り、成果物を受け取る
```

この型に合わない仕事では、操作数が増えないことを優先して変えてよい。その場合は `README.md` に理由を書く。

## 必須メタデータ

`page.md` の先頭にフロントマターとして置く。サイトのカード・一覧・絞り込みは、ここから生成する。

```yaml
---
id: minutes-from-transcript
title: 文字起こしから議事録を作る
summary: 会議の文字起こしを貼るだけで、決定事項・ToDo・持ち越し事項が整理された議事録を作ります。
category: meeting
status: Draft
version: 0.1.0
audience: [beginner, constrained-environment]
difficulty: 1                # 1〜3（★の数）
user_steps: 3                # 利用者の操作数
user_actions: [貼る, 答える, 仕上げる]
ai_knowledge: 不要
estimated_time: 約3〜5分（目標）
materials: [会議の文字起こし, 組織で利用が認められているチャット型のAI]
minimum_model: GPT-4.1
minimum_model_status: 未検証    # 未検証 / 検証中 / 確認済み
tested_models: []
last_tested: YYYY-MM-DD
input_types: []
output_types: []
confidentiality: 入力可否と注意事項
---
```

- `id` はフォルダ名（`name`）と同じにする
- `summary` はカードと一覧に表示する一文。利用者に向けて、です・ます調で書く
- `materials` は「用意するもの」。料理のレシピの材料のように、利用者が作業前にそろえるものを書く
- `minimum_model` には、最低動作モデルとして検証する（した）モデル名を書く。`minimum_model_status` が `確認済み` になるまでは、サイトでは「GPT-4.1（未検証）」「GPT-4.1（検証中）」のように状態を併記し、確認済みに見せない。`確認済み` にするのは、[evaluation.md](evaluation.md) の基準でテストし、結果を `README.md` に記録してから
- `estimated_time` は、実測前は `（目標）` を付ける。実測後は実測値に置き換える
- プロンプトの文字数はサイトが `prompts/` から計算して表示するため、メタデータには書かない
- `difficulty` と `user_steps` は、利用者の操作の負担を表す。内部の処理の複雑さではない
- カード（難易度・作業時間・最低動作モデル・操作数・AI知識）はサイトがこのメタデータから生成する。本文にカードを重ねて書かない

## page.md の本文（利用者向け）

サイトのRecipeページにそのまま表示する。です・ます調で、短く書く。

1. **使い方**：①〜③の各ステップに、利用者がすること（一文）、プロンプトへのリンク、返ってくるもの。②には回答の例と「分からないときは『不明です。そのまま進めてください』で大丈夫」
2. **長すぎて送れないとき**：文字数の上限で送れない場合の対処（[prompt-patterns.md](prompt-patterns.md) のP10）
3. **使う前に**：入力してはいけない情報と、置き換え方
4. **最後に確認すること**：人間が必ず確認する重要項目を、5項目程度のチェックリストで
5. **なぜうまくいくの？**：一度に頼むと何が起きるか、仕事をどう分けたかを、利用者向けに2〜3段落で。品質を左右する区別の例と、苦手なケースを短く添える。サイトでは折りたたんで表示する

詳しい設計、評価結果、改訂履歴は書かない。それらは `README.md` に書く。

## README.md の必須セクション（技術者向け）

GitHubでフォルダを開くと最初に表示される。サイトには表示せず、Recipeページの末尾から「設計・評価・改訂履歴を見る（GitHub）」としてリンクするだけにする。

1. **設計目標**：誰が、どのモデルで、何を、どの程度の時間で作れることを目指すか
2. **この仕事の分解**：一発で頼んだときにAIが同時に求められている仕事と、それをどう分けたか
3. **判断基準**：その仕事の品質を左右する区別の定義と、紛らわしい例
4. **中間フォーマット**：STEP 1で整理させる「箱」と、STEP 3での使われ方
5. **人間への確認**：質問の対象になる場面と、質問しなくてよい場面
6. **使っている設計パターン**：[prompt-patterns.md](prompt-patterns.md) のどのパターンをどう使っているか
7. **限界と注意点**：苦手な入力、品質が下がる条件、機密性、代替策
8. **動作確認モデルと評価**：モデル別の動作確認表、テストケース、その仕事に固有の評価指標、比較したいこと
9. **参考**
10. **改訂履歴**：日付、版、変更内容、変更理由

## 推奨

- 入力例・出力例（匿名化したもの）
- よくある失敗と対処
- 通常手順で品質が出ないモデル向けの「詳細モード」（処理を複数のプロンプトに分けた手順）。テストで必要と分かった場合に追加する
- コミュニティからのフィードバック

## 用語

Recipe間で共通して使う用語は次のとおり。その仕事に固有の用語（議事録の「決定事項」「ToDo」「持ち越し事項」など）は、各Recipeの `README.md` の「判断基準」で定義する。

| 用語 | 意味 |
|---|---|
| 不明 | 中間出力で、入力資料から確認できない項目 |
| 要確認 | 完成品で、人間の確認が必要なまま残っている項目 |
| 確認したいこと | STEP 1でAIが利用者に返す質問。重要な場合だけ出す |
| 中間フォーマット | STEP 1の整理結果の形。STEP 3の入力になる |

## Recipeの状態

| 状態 | 意味 |
|---|---|
| `Draft` | 手順案はあるが、評価が不十分 |
| `Tested` | テストセットで確認し、結果を記録済み |
| `Community-tested` | 複数の利用者または実際の現場で検証済み |
| `Stable` | 既知の制約が整理され、定期的な見直し対象になっている |

状態を上げるときは、`README.md` の評価結果と改訂履歴、`page.md` のメタデータを更新する。
