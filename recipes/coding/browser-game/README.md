# 設計と検証：AIと相談しながら、ブラウザーで遊べるゲームを作る

技術者・改善に参加したい人向けの文書。プロンプトがなぜこの形になっているのか、苦手なケース、評価方法を説明する。

利用者向けの使い方はWebサイトに表示する。その素材は [page.md](page.md)（カード・使い方・注意）と [prompts/](prompts/)（コピー用プロンプト）にある。

## 1. 設計目標

> **プログラミングの経験がない人が、チャット型のAIと相談しながら、HTMLファイル1つで動く小さなゲームを作り、機能の追加と不具合の修正を、壊さずに1つずつ進められること。**

「プログラミング」カテゴリの最初のRecipe。地域の子ども向けイベント、プログラミング教室、学校の授業、地域の魅力を伝える企画などで、「AIで何か作ってみる」最初の体験を想定している。

他のRecipeは「資料から事実を落とさず、作らずに成果物を作る」ことが中心だが、このRecipeは創作である。守るべきものは事実ではなく、**前に動いていた部分**である。

ゲームは題材であり、設計の中心は「企画 → 小さな試作品 → 1機能ずつ追加 → 原因を説明してから最小限の修正」という進め方そのものにある。クイズ、タイマー、くじ引きなど、ブラウザーで動く小さな道具にも同じ流れが使える。

## 2. この仕事の分解

「〇〇のゲームを作って」という短い指示の裏で、AIは次の仕事を同時に求められている。

1. 遊びのルールと流れを決める
2. 画面の構成を決める
3. コードを書く
4. 動作を確かめる
5. 利用者の「思っていたものと違う」に応える

一度に求めると、1と2が利用者の確認なしに決まり、5の手戻りが大きくなる。また、修正を頼むたびにAIが全体を書き直し、動いていた部分が壊れる（回帰）。4はAIにはできず、利用者が遊んで確かめるしかない。

```text
テーマ・遊ぶ人・中心の遊び
    ↓
STEP 1　企画の提案（コードなし）→ 企画まとめ　＋ 利用者が会話で調整
    ↓
STEP 2　企画まとめにあることだけで試作品 → 利用者が遊んで確かめる
    ↓
STEP 3　（必要なら）機能を1つ追加。ほかは変えない        ┐
STEP 4　（必要なら）原因を説明してから最小限の修正       ┘ 繰り返す
```

STEP 3と4は、どちらも「必要なら」で、利用者が何度でも繰り返す。基本の3ステップの型を4ステップに変えたのは、機能の追加と不具合の修正では、AIに守らせることが違うためである（追加は「指定以外を変えない」、修正は「原因を先に説明し、機能を加えない」）。

### 元の案からの変更

このRecipeは、「安芸高田の自然」をテーマにした小学生向けのゲームを例にした4つのプロンプトとして提案され、Gemini Argon で動作が確認された。4段階の構成、各段階の条件（HTML1ファイル、外部ライブラリなし、指定以外を作り直さない、原因を説明してから最小限に直す、確認する操作を3つ）は、その案を引き継いだ。次の点を変えた。

| 元の案 | 変更 | 理由 |
|---|---|---|
| テーマ・遊ぶ人・遊びがプロンプトに書き込まれている | `【例：…】` の欄にし、例のまま残っていたら質問させる | どの地域・テーマでも使えるようにする。元のテーマは `page.md` の入力例の考え方として残した |
| STEP 1の提案を、利用者がまとめてSTEP 2に貼る | STEP 1の最後に「企画まとめ」を出させ、STEP 2は同じ会話ならそのまま使う | 提案から試作品に入れるものを選ぶ作業は、初心者には負担が大きい。追加要素は企画まとめに入れさせず、STEP 3に回す |
| STEP 2「完成したブラウザーゲーム」 | 「試作品」 | STEP 1の「短時間で遊べる試作品」と揃え、最初から大きく作らせない |
| STEP 3・4で毎回HTMLを貼る | 同じ会話なら貼らなくてよい | 機能を足すほどHTMLが長くなり、送れなくなる（P10） |
| クリックのみ | クリックとタップの両方 | 「スマートフォンでも遊びやすく」と合わせるため |
| ― | キャラクターは絵文字や図形で表す | 外部画像を使わない条件の下で、AIが何で描くかを決めておく |
| ― | 個人の情報を入力・保存させない、外部へのリンクを入れない | 子どもが遊ぶことを想定するため |
| ― | 既存のゲーム・キャラクター・作品に似せない | 地域のイベントなどで配る・公開する場合の権利の問題を避ける |
| STEP 3は確認する操作なし | STEP 3にも確認する操作を3つ出させ、前からある機能を含める | 追加で壊れた部分（回帰）に気づけるようにする |
| STEP 4で原因が分からない場合の指示なし | 推測で大きく書き換えず、原因の候補と確かめる操作を書かせる | 原因が分からないまま書き換えると、別の不具合を生みやすい |
| ― | `page.md` に、HTMLの保存と開き方（Windows・Mac）を追加 | 初心者が最もつまずくのは、コードをファイルにして開くところ。Macのテキストエディットは標準でリッチテキストになるため、「標準テキストにする」が必要 |

## 3. 判断基準

### 追加と修正の範囲

| 頼まれたこと | 正しい範囲 | よくある誤り |
|---|---|---|
| コンボ得点を追加 | 得点の計算と表示だけを変える | 画面のデザインやタイマーまで書き直す |
| 再スタートで時間が2倍速になる | タイマーの止め忘れ（`clearInterval` の漏れなど）だけを直す | タイマー全体を作り直し、別の表示を壊す |
| 「もっと楽しく」 | 作る前に1つ質問する | 大量の機能を一度に足す |
| 原因が分からない不具合 | 原因の候補と、確かめる操作を返す | 推測で大きく書き換える |

### HTMLの全文を出させる理由

変更した部分だけを示させる方が短いが、初心者は「どこに貼り替えるか」が分からず、貼り間違えて壊すことが多い。このRecipeでは、長くなる代償を受け入れて、毎回全文を出させる。長くなりすぎた場合の対処は `page.md` の「長すぎて送れないとき」に書いた。

## 4. 中間フォーマット

- **企画まとめ**（STEP 1）：試作品に入れる内容だけの、10行程度の箇条書き。STEP 2の唯一の仕様になる
- **今のHTML**（STEP 2以降）：次のSTEPの入力になる。同じ会話なら直前の出力を使う
- **確認する操作**（STEP 2〜4）：利用者が遊んで確かめる手順。AIは動作を確かめられないため、確認の手順だけを出させる

## 5. 人間への確認

| 質問する場面 | 理由 |
|---|---|
| STEP 1の欄が例のまま | テーマや遊ぶ人が決まっていないまま提案すると、例のゲームができてしまう |
| STEP 3で、追加する機能の作り方が大きく分かれる | 「もっと楽しく」のような依頼で、AIが大きく作り直すのを防ぐ。質問は1つに限る |

そのほかは質問させない。企画の調整は、利用者が会話で自由に伝える。

## 6. 使っている設計パターン

共通のパターンは [docs/prompt-patterns.md](../../../docs/prompt-patterns.md) を参照。

| パターン | このRecipeでの使い方 |
|---|---|
| P1 処理の順序を固定する | 追加は「仕組みの確認 → 関係する部分の説明 → 追加」、修正は「原因の説明 → 最小限の修正」 |
| P3 禁止事項を具体的に書く | 指定以外の作り直し、外部の読み込み、個人の情報、外部リンク、既存作品への類似、修正での機能追加 |
| P4 分からないことの書き方を決める | 原因が分からない場合は、候補と確かめる操作を返す |
| P5 出力フォーマットを固定する | 企画まとめ、HTMLの全文（1つのコードブロック）、確認する操作3つ |
| P6 中間出力を次の入力にする | 企画まとめ → 試作品、今のHTML → 追加・修正 |
| P7 必要なときだけ質問する | 欄が例のままのとき、追加の作り方が大きく分かれるときだけ |
| P8 確認対象を指定してセルフチェック | 使わない。動作の確認はAIにはできないため、利用者が遊んで確かめる「確認する操作」に置き換えた |
| P10 文字数の上限に備える | 同じ会話ならHTMLを貼らない。途中で止まったときの対処と、ゲームを小さく保つことを `page.md` に書いた |

## 7. 限界と注意点

- AIはゲームを実際に動かして確かめられない。動作の確認は、利用者が遊んで行う
- 機能を足すほどHTMLが長くなり、AIの出力の上限に近づく。全文を出させる設計のため、長くなると途中で止まりやすい
- 同じ会話が長くなると、AIが古い版のHTMLを基に変更することがある。その場合は、最新のHTMLを貼り直す
- 絵文字の見た目は、端末やブラウザーによって違う
- 音、画像、得点の保存（ランキング）、複数人で遊ぶ機能は、このRecipeの範囲外である
- 作ったゲームをWebサイトで公開する方法（ホスティング）は扱わない
- アクセシビリティ（キーボードだけでの操作、色の見分けにくさへの配慮など）は、指定しなければ考慮されないことが多い

### テストケース

テストセット（`evals/`）は未作成。

| ケース | 内容 | 確かめること |
|---|---|---|
| 1. 標準 | 地元の生きものを見つけてタップする、小学生向け | 企画まとめ → 試作品が1回で動くか。5つの基本機能 |
| 2. 欄が例のまま | STEP 1を書き換えずに送る | 提案を始めず質問するか |
| 3. 機能の追加 | コンボ得点 → 残り10秒で速くなる → ハイスコア表示（同じ会話で3回） | 追加のたびに、前からある機能が壊れないか |
| 4. 不具合の修正 | 再スタートでタイマーが二重になるHTMLを渡す | 原因を説明し、タイマーの部分だけを直すか |
| 5. あいまいな追加 | 「もっと楽しくしてください」 | 1つだけ質問するか |
| 6. 別の題材 | 地域のクイズ（ゲームでない道具） | 同じ流れで使えるか |

### 評価指標

[docs/evaluation.md](../../../docs/evaluation.md) の基本評価項目に加えて、次を記録する。

| 評価項目 | 確認内容 |
|---|---|
| 動作 | 保存してすぐ遊べるか。スタート・得点・残り時間・終了・再スタートが動くか |
| 回帰のなさ | 機能の追加・修正のあとも、前からある機能が動くか |
| 変更の範囲 | 指定以外の部分（見た目、ほかの機能）を変えていないか |
| 条件の順守 | 外部の読み込み、個人の情報、外部リンクがないか |
| 出力の完全さ | HTMLが省略されず、1つのコードブロックで全文出ているか |
| 説明の分かりやすさ | 原因と変更の説明が、プログラミングの経験がない人に分かるか |
| 端末 | スマートフォンの縦の画面で、指で遊べるか |
