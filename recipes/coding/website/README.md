# 設計と検証：AIと相談しながら、1ページのWebサイトを作る

技術者・改善に参加したい人向けの文書。プロンプトがなぜこの形になっているのか、苦手なケース、評価方法を説明する。

利用者向けの使い方はWebサイトに表示する。その素材は [page.md](page.md)（カード・使い方・注意）と [prompts/](prompts/)（コピー用プロンプト）にある。

## 1. 設計目標

> **Web制作の経験がない人が、作りたいサイトの目的と載せたい内容を短く書くだけで、事実を作らず、スマートフォンに対応した1ページのWebサイトを、ビルドなしで作れること。**

「プログラミング」カテゴリの2本目のRecipe。地域団体の活動紹介、イベントの案内、教室の募集、個人のポートフォリオなど、1ページで完結するサイト（ランディングページ）を対象にする。

[ブラウザーで遊べるゲームを作る](../browser-game/) と同じく「設計 → 作る → 1つずつ直す」の流れを取るが、Webサイトには**載せる文章が事実である**という、ゲームにはない制約がある。このため、[notice-from-memo](../../writing/notice-from-memo/) などの文章のRecipeと同じく、事実を作らないことを最優先にしている。

## 2. この仕事の分解

「〇〇のWebサイトを作って」という短い指示の裏で、AIは次の仕事を同時に求められている。

1. サイトの目的と、見た人にしてほしいこと（申込など）を決める
2. セクションの構成と、載せる文章を決める
3. 色・文字・余白などのデザインを決める
4. スマートフォン対応、動き、アクセシビリティ、SEOなどの技術の条件を守る
5. コードを書く

一度に求めると、2で事実（実績、料金、利用者の声、住所）が作られ、1の申込の導線が、どこにもつながらないボタンやフォームになる。一方、1〜4をすべて利用者に指定させると、元の案のように約60項目の記入が必要になる。

そこで、1〜3は「サイトの設計書」としてAIに下書きさせ、利用者が確認する。4は利用者が触らない固定の条件として、STEP 3のプロンプトに持たせる。

```text
作りたいサイトのメモ（＋載せたい文章、参考サイト）
    ↓
STEP 1　把握 → 設計書（メモの文章はそのまま、考えた文章は【仮】、考えた項目は（提案））（＋必要な場合だけ質問）
    ↓
STEP 2　利用者が質問に答え、（提案）【仮】を直す
    ↓
STEP 3　設計書 ＋ 固定の技術の条件で、サイトを作る
    ↓
STEP 4　（必要なら）直したいところだけを直す
```

### 元の案からの変更

このRecipeは、Webサイトの要件をすべて記入する約60項目のテンプレートとして提案された。作成者自身が「指定するのはかなりややこしい」として、[illustration](../../design/illustration/) と同じ提案型にすることを希望した。

元の案の「掲載するコンテンツ」「デザイン要件」「レイアウト要件」は、STEP 1の設計書の項目にした。「基本方針」「参考資料」「スクロール・インタラクション」「アクセシビリティ」「技術要件」「SEOと共有設定」「出力形式」は、ほぼそのままSTEP 3の固定の条件にした。次の点を変えた。

| 元の案 | 変更 | 理由 |
|---|---|---|
| 利用者が約60項目を記入する | 利用者は8行程度のメモを書き、AIが設計書に展開する | 記入の負担が大きすぎる。技術の条件は利用者が判断できないため、固定にする |
| 不足は「仮置きまたは要確認」 | AIが考えた文章は【仮】を付け、**サイトの上でも【仮】を表示したまま**にする | 仮の文章がコードの中で見分けられなくなると、そのまま公開されやすい。表示に残せば、開いた人が必ず気づく |
| ファイルは3つ（index.html、styles.css、script.js） | A：1つにまとめる（おすすめ）、B：3つに分ける、を選べるようにした | 初心者には、3つのファイルを正しい名前で同じフォルダに保存するのが難しい。ゲームのRecipeと同じ保存方法で開けるようにする |
| ― | 送信の仕組みが必要な入力フォームは作らず、既存の申込フォームやメールへのリンクにする | このサイトだけでは送信できないため、AIが作ったフォームは、送ったつもりで誰にも届かない |
| 外部ライブラリ・CDNは指定がない限り使わない | Webフォント、アクセス解析のコードも読み込まない | 外部との通信をなくし、ファイルを開くだけで同じ表示にする。訪問者の情報が外部に送られないようにする |
| OGPの基本設定 | URLと共有用の画像が決まっていない場合は「要確認」にする | OGPには公開先のURLが必要で、AIがそれらしいドメインを作りやすい |
| 外部画像を使う場合は出典を書く | 画像は使わず、差し替え用の枠を作る | 外部画像の権利と、リンク切れの問題を避ける。イラストは [illustration](../../design/illustration/) で作って差し替える |
| リンク先が不明 | `#` にして「要確認」のコメントを付ける | 推測のURLを入れない |
| デザイン要件（色・フォント・角丸・影・余白など）を利用者が指定する | 「デザインの型」（A：デジタル庁デザインシステム、B：Material Design 3）を選ばせ、余白・文字・色の数などの共通の決まりをSTEP 3に固定で持たせる | 3章「デザインの型」 |
| ― | STEP 4として、直したいところだけを直すプロンプトを追加。変更したファイルだけを全文で出す | ゲームのRecipeと同じ理由。3ファイルの場合、毎回すべてを出すと長くなりすぎる |

## 3. 判断基準

### メモと設計書の印

| 内容 | 印 | サイトでの扱い |
|---|---|---|
| メモに書かれた文章・固有名詞・日時・金額・連絡先 | なし | そのまま載せる |
| AIが考えたサイトに載る文章（キャッチコピー、セクションの説明など） | 【仮】 | 【仮】を付けたまま表示する |
| AIが考えたデザイン・構成 | （提案） | 設計書でだけ示す。サイトには出ない |
| メモにないリンク先・公開先 | 要確認 | リンクは `#` とコメント |
| メモにない事実（実績、料金、利用者の声、住所） | ― | 作らない |

紛らわしい例：

| メモの例 | 正しい扱い | よくある誤り |
|---|---|---|
| 「体験会に申し込んでほしい」（申込方法なし） | 質問する。答えがなければ、ボタンのリンク先を要確認 | 入力フォームを作る |
| 「講師の紹介」（紹介文なし） | 【仮】の紹介文、または質問 | 経歴や資格を作る |
| 「よくある質問」（質問なし） | 【仮】の質問と回答 | 料金や対象年齢など、事実を含む回答を【仮】なしで書く |
| 「参加者の声を載せたい」（声なし） | 要確認として一覧に残す | それらしい声を作る |

### デザインの型

デザインの経験がない利用者でも、ある程度整った見た目になるよう、公開されているデザインシステムの「考え方」を2つから選ばせる。

| 型 | 選んだ理由 |
|---|---|
| A：[デジタル庁デザインシステム](https://design.digital.go.jp/) | 日本語のWebサイト向けで、読みやすさとアクセシビリティを重視している。地域団体・学校・公共的な案内に合う。公開データはCC BY 4.0（[利用上の注意](https://design.digital.go.jp/introduction/notices/)） |
| B：[Material Design 3](https://m3.material.io/) | 広く知られており、古いモデルでも特徴（角丸のカード、基調色からの配色、控えめな影）を再現しやすい |

ただし、モデルがデザインシステムの細かい値（色の番号、文字の大きさの段階）を正確に覚えているとは限らない。名前だけを渡すと、もっともらしい値を作るか、特徴の薄い見た目になる。そこで、STEP 3には、どちらの型にも共通する具体的な決まり（余白は8pxの倍数、本文16px以上、行間1.7前後、色は基調色・アクセント・グレーだけ、コントラスト比4.5:1以上、押せる大きさ44px以上など）を数値で書いた。型は方向性、共通の決まりは品質の下限という役割分担である。

外部のCSSやコンポーネントは読み込まない（基本方針の「外部を読み込まない」を保つ）。また、デジタル庁デザインシステムの見た目は行政のサイトを連想させるため、ロゴ・名前の表示と、公式のサイトと誤解される見た目・文言を禁止した。

## 4. 中間フォーマット

STEP 1の「サイトの設計書」。目的、ヒーロー、セクション構成、ボタン、フッター、デザイン、レイアウト、未確定の情報の8つの見出し。STEP 3は、この設計書と利用者の変更だけを根拠にする。

STEP 3の出力の最後の「【仮】の文章、要確認の項目、差し替えが必要な画像の一覧」は、公開前の作業の一覧になる。

## 5. 人間への確認

| 質問する場面 | 理由 |
|---|---|
| 見た人にしてほしいことが分からない | サイトの構成とボタンが決まらない |
| 申込・問い合わせの方法が分からない | ボタンのリンク先がなく、サイトとして機能しない |
| メモの情報が食い違っている | どちらが正しいかは作成者にしか分からない |

デザインや構成の好みは質問しない。（提案）として書かせ、利用者が変えたいときだけ伝える。

## 6. 使っている設計パターン

共通のパターンは [docs/prompt-patterns.md](../../../docs/prompt-patterns.md) を参照。

| パターン | このRecipeでの使い方 |
|---|---|
| P1 処理の順序を固定する | 把握 → 設計書 → 確認 |
| P2 分類は定義で渡す | メモの文章（印なし）、考えた文章（【仮】）、考えた項目（（提案））、不明なリンク（要確認） |
| P3 禁止事項を具体的に書く | 実績・料金・住所・利用者の声の作成、メモの文章の言い換え、リンク先の推測、送信フォーム、外部の読み込み |
| P4 分からないことの書き方を決める | 【仮】をサイトの表示に残す。リンクは `#` と要確認のコメント |
| P5 出力フォーマットを固定する | 設計書の8つの見出し。STEP 3の出力の順番 |
| P6 中間出力を次の入力にする | 設計書を、STEP 3の唯一の根拠にする |
| P7 必要なときだけ質問する | してほしいこと、申込の方法、食い違いに限定。3つまで |
| P9 入力の区切りと念押し | メモを `↓↓↓` `↑↑↑` で囲み、メモの後で「事実を作らない」を再確認させる |
| P10 文字数の上限に備える | 同じ会話ならコードを貼らない。途中で止まったときに、ファイルを1つずつ出させる方法を `page.md` に書いた |

## 7. 限界と注意点

- 見るための1ページだけを作る。複数のページ、申込の受付、ログイン、データベースは扱わない
- 公開（ホスティング、ドメイン）の方法は扱わない
- コードが長くなりやすく、AIの返答が途中で止まることがある
- アクセシビリティの条件は指示しているが、色のコントラストなどが十分かは、人間が確認する必要がある
- 端末に入っているフォントを使うため、端末によって見た目が少し違う
- 生成されたコードの品質（セキュリティを含む）は保証されない。とくに、後から入力フォームや外部のサービスを足す場合は、専門家の確認を受ける

### 評価指標

[docs/evaluation.md](../../../docs/evaluation.md) の基本評価項目に加えて、次を記録する。

| 評価項目 | 確認内容 |
|---|---|
| 事実性 | メモにない実績・料金・住所・利用者の声・リンク先を作っていないか |
| 原文の保持 | メモの文章・固有名詞が、一字も変わっていないか |
| 印の正しさ | 考えた文章に【仮】、考えた項目に（提案）が付き、【仮】がサイトに表示されているか |
| 申込の導線 | 送信フォームを作らず、設計書のリンクになっているか |
| 動作 | ファイルを開くだけで表示されるか。スマートフォンの幅で横にはみ出さないか |
| 動きの条件 | 表示の動きが一度だけで、reduced-motion で止まり、JavaScriptが動かなくても内容が見えるか |
| 外部の読み込み | 外部のライブラリ・フォント・解析のコードがないか |
| 変更の範囲 | STEP 4で、指定以外が変わっていないか |
