# 設計と検証：文字起こしから議事録を作る

技術者・改善に参加したい人向けの文書。プロンプトがなぜこの形になっているのか、苦手なケース、評価方法を説明する。

利用者向けの使い方はWebサイトに表示する。その素材は [page.md](page.md)（カード・使い方・注意）と [prompts/](prompts/)（コピー用プロンプト）にある。

## 1. 設計目標

> **忙しい初心者が、GPT-4.1でも、文字起こしから短時間で正確な議事録を作れること。**

「高性能なプロンプト」を目指すのではなく、**利用者の総作業時間を最小化する**ことを重視する。

- **分かりやすい**：どこに文字起こしを貼るのか、次に何をするのか、質問されたらどうするのかが明確で、プロンプトの専門知識を必要としない
- **手順が少ない**：「貼る → 必要なら答える → 仕上げる」の3ステップ。質問がなければ実質2ステップ
- **作業時間が短い**：決定事項・ToDo・担当者・不明点を探す作業を利用者に求めない

## 2. この仕事の分解

「この文字起こしから議事録を作成してください」という短い指示の裏で、AIは次の仕事を同時に求められている。

1. 文字起こしを理解する
2. フィラーや雑談を除外する
3. 重要情報を抽出する
4. 議題を識別する
5. 意見と決定を区別する
6. ToDoを識別する
7. 担当者・期限を判断する
8. 不明情報を処理する
9. 内容を要約する
10. 読みやすい文章に編集する

これを一度に求めると、AIが不足している情報を自然な文章で補ってしまい、誤りに気づきにくくなる。そこで、利用者の操作は増やさずに、処理を次のように分ける。

```text
文字起こし
    ↓
STEP 1　抽出・判定・構造化（＋必要な場合だけ質問）
    ↓
重要な不足情報はある？
   ↙           ↘
 ある           ない
  ↓              │
STEP 2           │
人間が回答       │
  ↓              │
  └──────┬───────┘
         ↓
STEP 3　議事録として編集（＋セルフチェック）
         ↓
        完成
```

最初から「きれいな議事録」を作らせず、**事実認定と文章作成をできるだけ分離する**ことが、この設計の中心である。

## 3. 判断基準

議事録の正確さは、次の区別ができるかどうかに直結する。プロンプトでは分類の名前だけでなく、定義を渡している。

| 分類 | 定義 |
|---|---|
| 議論・意見 | 会議中に出された説明、意見、質問、提案 |
| 結論 | その議題について、最終的にどのような状態になったか |
| 決定事項 | 会議として明確に合意・確定したこと |
| ToDo | 会議後に誰かが実行・確認・対応すること |
| 持ち越し事項 | 結論が出ず、今後判断・検討・確認すること |

例：

| 発言 | 分類 |
|---|---|
| 「来月から始めた方がいいと思います」 | 議論・意見（提案） |
| 「では来月1日から開始します」 | 決定事項 |
| 「田中さん、今月末までにマニュアルを作成してください」 | ToDo |

分からないことの書き方も決めている。STEP 1では「不明」、STEP 3では「要確認」、該当がない場合は「なし」と書かせる。

## 4. 中間フォーマット

STEP 1では、情報を次の「箱」に整理させる。

- 会議情報（会議名・日時・参加者）
- 議題と議論（議題ごとの主な議論・意見・結論）
- 決定事項
- ToDo（担当者・内容・期限）
- 持ち越し事項
- その他の重要事項
- 確認したいこと

これは人間が読みやすくするためだけではない。**STEP 1の出力そのものを、STEP 3が利用する中間データにする**ことが目的である。STEP 3では、長い文字起こしをゼロから解釈し直すのではなく、構造化済みの情報を議事録に編集することに集中させる。

```text
生の文字起こし → 構造化された事実 → 必要なら人間が補完 → 完成版議事録
```

## 5. 人間への確認

AIには文字起こしだけでは判断できないことがある。例えば「田中さん、例の件よろしく」だけでは、「例の件」の内容や期限が分からない。推測させれば誤った議事録になり、すべて質問させれば利用者の負担が増える。

| 状況 | 処理 |
|---|---|
| AIだけで判断できる | AIが処理する |
| AIでは判断できず、議事録上重要 | 人間に質問する |
| 不明だが議事録への影響が小さい | 質問せずに進める |

このRecipeで質問の対象になり得るのは次の場合である。

- 決定したのか、単なる提案なのか判断できない
- 重要なToDoの担当者・期限が分からない
- 固有名詞の誤変換が疑われ、意味が変わる可能性がある
- 誰の発言かによって意味が大きく変わる

回答は自由な短文でよく、「不明です。そのまま進めてください」でもよい。候補が絞れる場合は、AIに選択肢を添えさせ、利用者が選ぶだけで済むようにしている。

## 6. 使っている設計パターン

共通のパターンは [docs/prompt-patterns.md](../../../docs/prompt-patterns.md) を参照。

| パターン | このRecipeでの使い方 |
|---|---|
| P1 処理の順序を固定する | STEP 1を「抽出 → 判定 → 整理 → 確認」の順に固定 |
| P2 分類は定義で渡す | 議論・意見／結論／決定事項／ToDo／持ち越し事項の定義（3章） |
| P3 禁止事項を具体的に書く | 担当者・期限の推測、提案の決定扱い、固有名詞の勝手な修正など8項目 |
| P4 分からないことの書き方を決める | 「不明」「要確認」「なし」 |
| P5 出力フォーマットを固定する | STEP 1の整理形式、STEP 3の議事録形式 |
| P6 中間出力を次の入力にする | STEP 1の整理結果をSTEP 3の根拠にする（4章） |
| P7 必要なときだけ質問する | 議事録上重要な不足情報に限定（5章） |
| P8 確認対象を指定してセルフチェック | STEP 3の最終確認5項目。確認作業は出力させない |
| P9 入力の区切りと念押し | 文字起こしを `↓↓↓` `↑↑↑` で囲み、文字起こしの後で原則を再確認させる |

### セルフチェックの対象

STEP 3では「よく確認してください」ではなく、議事録で典型的な次の5つの失敗を指定して確認させる。

1. 推測による事実の追加
2. 意見・提案と決定事項の混同
3. 決定事項とToDoの混同
4. 重要な決定事項・ToDo・持ち越し事項の欠落
5. 不明な担当者・期限の確定表現

## 7. 限界と注意点

このRecipeは、AIに任せれば必ず正しい議事録ができることを保証しない。**AIに任せられる範囲を最大化し、人間が介入する範囲を最小化する**ためのものである。

特に次のケースには限界がある。

- 元の文字起こし自体が誤っている、話者の識別が間違っている
- 会議そのものの結論が曖昧である
- 「あれ」「それ」「例の件」などの指示語が多い
- 固有名詞が大きく誤変換されている
- 会議の外で決まった事項や、資料だけで示された情報、うなずきなど言葉にならない合意が文字起こしに含まれていない
- 長い会議では、1回の入力に収まらない、または抜けが増える可能性がある。その場合は議題ごとに文字起こしを分けて使う

機密性の高い会議内容は、利用する環境の規定を確認する。

## 8. 動作確認モデルと評価

### 動作確認モデル

| モデル | 動作確認 | 評価 | 確認日 |
|---|---|---|---|
| GPT-4.1 | 未検証 | — | — |

### テストケース

| ケース | 内容 | 確かめること |
|---|---|---|
| 1. 普通の会議 | 決定事項、担当者、期限が明確 | 基本動作 |
| 2. 曖昧な会議 | 「それでいいですかね」「そうですね」など曖昧な合意が多い | 曖昧な合意を決定扱いせず、質問か持ち越しにできるか |
| 3. 意見が対立する会議 | 賛成・反対・保留が混在する | 意見と結論を混同しないか |
| 4. 文字起こし品質が悪い会議 | 誤変換、フィラー、話者不明、言い直しが多い | 固有名詞を勝手に直さず、必要なら質問できるか |
| 5. 途中で結論が変わる会議 | 前半で「A」とした後、終盤で「やはりB」に変わる | 最終的な「B」を決定事項にできるか |

テスト用の文字起こしは、匿名化したダミーデータで作り、`evals/` に置く。

### 評価指標

[docs/evaluation.md](../../../docs/evaluation.md) の基本評価項目に加えて、次を記録する。

| 評価項目 | 確認内容 |
|---|---|
| 事実性 | 文字起こしにない情報を追加していないか |
| 決定事項精度 | 意見・提案を決定と誤認していないか |
| ToDo精度 | 担当者・内容・期限を正しく抽出できたか |
| 持ち越し精度 | 未決定事項を正しく残せたか |
| 網羅性 | 重要事項を落としていないか |
| 質問品質 | 本当に必要なことだけ質問しているか |
| 作業時間 | 利用者の操作・修正時間を短縮できたか |

### 比較したいこと

- **根拠付き版との比較**：STEP 1の決定事項とToDoに、根拠となる発言の引用を付けさせた版と比べる。照合しやすさは上がるが、出力が長くなり、利用者の読む時間が増える可能性がある
- **一発生成との比較**：「この文字起こしから議事録を作成してください」だけの場合と比べ、手順を分けた効果を確かめる

GPT-4.1を最低基準としてテストし、失敗したケースをもとにプロンプトを修正する。結果がまとまるまでは `Draft` のまま扱う。
