# 設計と検証：利用規約・約款から、確認すべき条項を整理する

技術者・改善に参加したい人向けの文書。プロンプトがなぜこの形になっているのか、苦手なケース、評価方法を説明する。

利用者向けの使い方はWebサイトに表示する。その素材は [page.md](page.md)（カード・使い方・注意）と [prompts/](prompts/)（コピー用プロンプト）にある。

## 1. 設計目標

> **忙しい実務者が、GPT-4.1でも、利用規約や約款から、自分がすること・してはいけないこと、お金と解約、事業者の権限と責任の範囲、入力した情報の扱いを、条項の番号と原文つきで短時間に把握できること。**

「読み解く」カテゴリの2本目のRecipe。個人として、または組織でサービスの導入を検討するときに、クラウドサービス・アプリ・サブスクリプションの利用規約や、保険・サービスの約款を読む場面を対象にする。

- **判断はしない**。条項が有利か不利か、有効か無効か、契約してよいかは、利用者の目的・組織のルール・専門家の判断で決まる。このRecipeは、その判断のために「どこに何が書かれているか」を整理するところまでを担う
- 原文を読まずに済ませるためではなく、**原文のどこを読めばよいかを絞り込む**ためのもの

## 2. この仕事の分解

「この規約を要約して」という短い指示の裏で、AIは次の仕事を同時に求められている。

1. 文書の名称・事業者・改定日・対象のサービスを把握する
2. 条項を種類ごとに振り分ける（利用者の義務、禁止、料金・解約、事業者の権限、責任の範囲、データ・権利）
3. 例外や条件（ただし書き）を、条項とセットで保持する
4. 見落としやすい条項を見つける
5. 原文の表現を、意味を変えずに示す
6. 条項の番号を保持する
7. 読みやすく編集する

一度に求めると、3と5が崩れやすく、さらに求めていない「判断」が加わりやすい。要約は、文章を短くするほど「ただし、故意又は重大な過失による場合を除く」のような例外を落とす。また、「一般的な規約です」「特に問題はありません」のような評価を付け加えやすい。そこで、他の読み解くRecipeと同じく、STEP 1で抽出・分類・整理を行い、STEP 3で編集する。

```text
規約・約款
    ↓
STEP 1　把握 → 抽出と分類 → 確認ポイント（原文の抜き出し）→ 整理（＋必要な場合だけ質問）
    ↓
STEP 2　利用者が、欠けている文書・プランについて答える
    ↓
STEP 3　整理した情報だけでまとめに編集（＋セルフチェック）
```

## 3. 判断基準

### 条項の種類

| 種類 | 定義 | 文の形の例 |
|---|---|---|
| 利用者の義務 | 利用者が行うよう求められていること | 「利用者は、〜しなければならない」「〜するものとする」 |
| 禁止事項 | 利用者が行ってはいけないこと | 「利用者は、〜してはならない」 |
| 料金・期間・解約 | 料金、支払い、契約期間、自動更新、解約、返金、違約金 | 「月額料金は」「自動的に更新」「返金しない」 |
| 事業者の権限 | 事業者ができるとされていること | 「当社は、〜できるものとする」 |
| 責任の範囲 | 事業者が責任を負わない場合、賠償の上限 | 「一切の責任を負わない」「〜を上限とする」 |
| データ・権利 | 入力した情報や個人情報の利用・提供、投稿したものの権利 | 「サービスの改善に利用」「無償で利用を許諾」 |
| その他 | 紛争の解決、裁判所など | 「〇〇地方裁判所を専属的合意管轄」 |

議事録やガイドラインのRecipeと違い、主語に注目させている。規約では、同じ「〜できる」でも、利用者ができるのか事業者ができるのかで、意味がまったく変わるためである。

### 確認ポイント

確認ポイントは、AIの評価ではなく、**書かれ方で決まる客観的な基準**で選ばせる。

| 基準 | 理由 |
|---|---|
| 自動更新、解約の期限・手数料・違約金、返金しない | お金に直結し、気づいたときには手遅れになりやすい |
| 事業者が規約・料金を一方的に変更できる | 今の条件が将来も続くとは限らない |
| 事業者が責任を負わない、賠償に上限がある | 問題が起きたときの扱いが決まる |
| 入力した情報を改善・学習・第三者提供に使う | 組織の情報を入力する場合、情報の管理に関わる |
| 投稿・入力したものの権利を譲渡・許諾する | 作ったものを自由に使えなくなる場合がある |

「不利な条項を挙げて」と指示すると、AIは不利かどうかを判断し始める。判断の基準は利用者の立場で変わるうえ、AIが「不利ではない」と判断したものは挙げられなくなる。書かれ方で選ばせれば、判断を伴わず、挙げ漏れも検証しやすい。

### 原文の抜き出し

確認ポイントには、原文を40字以内でそのまま抜き出させる。規約は、言い換えで意味が変わりやすい（「責任を負わない」と「責任を負わない場合がある」は違う）。40字は、表の1セルに収まり、条項の要点の文を1つ抜き出せる長さとして置いた。

## 4. 中間フォーマット

STEP 1では次の「箱」に整理させる。

- 文書情報（名称・事業者・最終改定日・施行日・対象のサービス・プラン）
- 条項の整理の表（種類・内容・条項）
- 確認ポイントの表（当てはまる理由・原文の抜き出し・条項）
- 確認したいこと

STEP 3では、確認ポイントを先頭に置く。利用者がまず原文と照らし合わせるべき場所だからである。

## 5. 人間への確認

| 質問する場面 | 理由 |
|---|---|
| 文書の一部しか貼られていない | Webページのコピーで途中が抜けることが多い。抜けたまま整理すると「解約の条件がない」と誤って伝わる |
| 料金表・別紙・別の規約を参照している | 「料金は別表のとおり」のように、肝心の条件が別の文書にあることが多い |
| プランや利用者の種類で条件が変わる | 個人向けと法人向け、無料プランと有料プランで、条件が違うことがある |

条項の解釈（「この条項はどういう意味か」）について質問させることはしない。解釈は、事業者や専門家が判断することだからである。

## 6. 使っている設計パターン

共通のパターンは [docs/prompt-patterns.md](../../../docs/prompt-patterns.md) を参照。

| パターン | このRecipeでの使い方 |
|---|---|
| P1 処理の順序を固定する | 把握 → 抽出と分類 → 確認ポイント → 整理 → 確認 |
| P2 分類は定義で渡す | 条項の種類を、主語と文の形の例つきで定義。確認ポイントを、書かれ方の基準で定義（3章） |
| P3 禁止事項を具体的に書く | 有利・不利、有効・無効、契約してよいかの判断、ただし書きの省略、抜き出しの書き換え |
| P4 分からないことの書き方を決める | 「不明」「要確認」。貼られていない文書は「原文で確認すべきこと」に残す |
| P5 出力フォーマットを固定する | 条項の整理の表、確認ポイントの表（理由・原文・条項） |
| P6 中間出力を次の入力にする | STEP 1の確認ポイントの表を、STEP 3でそのまま使う |
| P7 必要なときだけ質問する | 文書の欠け、別紙の参照、プランの違いに限定（5章） |
| P8 確認対象を指定してセルフチェック | 推測の追加、ただし書きの欠落、条項番号の欠落、判断の混入、抜き出しの書き換え |
| P9 入力の区切りと念押し | 文書を `↓↓↓` `↑↑↑` で囲み、文書の後で「判断ではなく整理」を再確認させる |
| P10 文字数の上限に備える | 文書の欄が空のときは待つ指示。`page.md` に、分けて送る方法（条の前で区切る）と、気になる条項だけを使う方法を載せる |

### 決まった一文を必ず書かせる理由

STEP 3の最後に「このまとめは条項の整理であり、契約してよいかや、条項が有効かの判断は含みません。」を、そのまま書かせている。まとめが組織の中で転送されたとき、受け取った人が「AIが確認済み」と誤解しないようにするためである。

## 7. 限界と注意点

- このRecipeは条項の整理であり、法的な判断・解釈・助言はしない
- 消費者契約法など、法律によって条項が無効になる場合があるが、それは判断しない
- 料金表、プライバシーポリシー、個別の利用規約など、別の文書に書かれた条件は、貼られていなければ分からない
- 規約の改定は頻繁に行われる。最新の版であるかは、AIには判断できない
- Webページからのコピーでは、折りたたまれた部分や、別ページに分かれた条項が抜けることがある
- 長い規約では、1回の入力に収まらないことが多い。分割して送ると、後半の抜けが増える可能性がある

### テストケース

実在のサービスの規約を使うと、改定で内容が変わり、正解が古くなる。また、特定の事業者の規約を評価しているように見えるおそれがある。テスト用には、架空の事業者による架空の規約を使う。1〜6は [evals/](evals/) に作成済み。

| ケース | 内容 | 確かめること |
|---|---|---|
| 1. 標準 | 短いクラウドストレージの利用規約 | 基本動作。種類の振り分けと条項番号 |
| 2. 自動更新・解約 | 有料の学習サービスの規約 | 解約の期限・返金・違約金を、日数や金額を変えずに示せるか |
| 3. 入力データの扱い | AI翻訳サービスの規約 | 学習への利用、利用しない設定の方法、保存期間を示せるか |
| 4. 免責と例外 | 免責・責任の上限・一方的な変更が多い規約 | ただし書きを落とさないか |
| 5. 保険の約款 | 傷害保険の約款の抜粋 | 保険金が支払われない場合、告知の義務、請求の期限を示せるか |
| 6. 別表の参照と途中で切れた文書 | 「料金は別表のとおり」で、別表がなく、途中で切れている | 欠けている文書を質問できるか |

### 評価指標

[docs/evaluation.md](../../../docs/evaluation.md) の基本評価項目に加えて、次を記録する。

| 評価項目 | 確認内容 |
|---|---|
| 振り分けの正確さ | 利用者の義務と事業者の権限を取り違えず、種類どおりに振り分けたか |
| 確認ポイントの網羅 | 基準に当たる条項を挙げ漏れていないか |
| 例外の保持 | ただし書きを、条項とセットで残せたか |
| 数値の正確さ | 日数・金額・期間・上限を、原文どおりに示せたか |
| 原文の保持 | 確認ポイントの抜き出しが、原文と一字一句一致しているか |
| 判断の混入の有無 | 有利・不利、有効・無効、契約してよいかの判断を書いていないか |
| 条項番号の正確さ | 条項の番号が原文と一致しているか |
