# 設計と検証：メモからお知らせ文を作る

技術者・改善に参加したい人向けの文書。プロンプトがなぜこの形になっているのか、苦手なケース、評価方法を説明する。

利用者向けの使い方はWebサイトに表示する。その素材は [page.md](page.md)（カード・使い方・注意）と [prompts/](prompts/)（コピー用プロンプト）にある。

## 1. 設計目標

> **忙しい実務者が、GPT-4.1でも、行事や手続きのメモから、読み手が迷わず行動できるお知らせ文を、事実を作らずに短時間で作れること。**

「文章作成」カテゴリの最初のRecipe。自治体・地域団体・学校・企業などで繰り返し発生する、住民・会員・保護者・職員向けのお知らせ（行事の案内、手続きの案内、変更・中止の連絡）を対象にする。

- 文章をきれいに整えることより、**必要な情報がそろっていて、メモにない情報が入っていないこと**を優先する
- 情報が足りないときは、文章を完成させるより、**足りないことを利用者に気づかせる**ことを優先する

## 2. この仕事の分解

「このメモからお知らせを作って」という短い指示の裏で、AIは次の仕事を同時に求められている。

1. 何のお知らせか、誰に向けたものかを把握する
2. メモの情報を、日時・場所・対象・内容・申込方法・問い合わせ先などに振り分ける
3. 読み手が行動するのに足りない情報に気づく
4. メモの中の食い違いに気づく
5. 条件や注意事項（雨天時、先着順、締切）を保持する
6. 読み手に合った言葉づかいを選ぶ
7. 読みやすく編集する

一度に求めると、3と4が崩れやすい。文章を完成させようとするほど、足りない情報（申込締切、問い合わせ先の電話番号など）をそれらしく補い、食い違う情報の片方を黙って選ぶためである。読みやすく書かれているほど、作られた情報に気づきにくい。そこで他のRecipeと同じく、STEP 1で整理と点検を行い、STEP 3で編集する。

```text
メモ
    ↓
STEP 1　把握 → 抽出 → 項目の整理（記載あり／不足／矛盾）（＋必要な場合だけ質問）
    ↓
STEP 2　利用者が不足を補う、読み手を選ぶ、書かない項目を決める
    ↓
STEP 3　整理した情報だけでお知らせ文に編集（＋セルフチェック）
```

## 3. 判断基準

この仕事の品質は、各項目の「状態」の判定でほぼ決まる。

| 状態 | 意味 | STEP 3での扱い |
|---|---|---|
| 記載あり | メモに書かれている | メモの表記のまま使う |
| 不足 | 読み手が行動するのに必要だが、メモにない | 利用者が答えれば使う。答えがなければ【要確認：○○】と残す |
| 矛盾 | メモの中で食い違っている（開始時刻が2つある、など） | どちらかに決めず質問する。答えがなければ【要確認】と残す |

「必要な項目」は、お知らせの種類で変わる。無料の行事に費用の項目は要らず、申込不要の行事に締切は要らない。このため、項目の一覧を固定の必須項目にはせず、「読み手が行動するのに必要か」で判断させている。

紛らわしい例：

| メモの例 | 正しい扱い | よくある誤り |
|---|---|---|
| 「3/15（日）10時〜」 | 記載あり。曜日もメモのまま | 年や曜日を補う、曜日を計算し直す |
| 「申込は電話で」（番号なし） | 不足（電話番号） | それらしい番号や「担当課まで」を作る |
| 「雨天中止」 | 条件として保持 | 要点の欄に入らず落ちる |
| 「10時開始」と別の行に「10:30〜」 | 矛盾として質問 | どちらかを黙って採用する |
| 「6/1 → 6/8に変更」 | 変更前・変更後として保持 | 変更前の日付を案内の日付として書く |

### 曜日を扱わない理由

GPT-4.1を含む多くのモデルは、日付から曜日を正確に計算できないことがある。曜日の誤りは、お知らせで最も多い誤りの1つであり、利用者が気づきにくい。このため、メモにない曜日は付け加えさせず、日付と曜日の照合は「最後に確認すること」で人間が行う。

## 4. 中間フォーマット

STEP 1では次の「箱」に整理させる。

- お知らせの概要（種類、読み手）
- 項目の整理の表（項目・メモの記載・状態）
- 確認したいこと

表の「メモの記載」の列は、言い換えずにメモの表現のまま書かせる。STEP 3で日時や連絡先の表記が変わるのを防ぐため。

## 5. 人間への確認

| 質問する場面 | 理由 |
|---|---|
| 読み手が行動するのに必要な情報が不足している | 日時・場所・申込方法・締切・問い合わせ先がないと、お知らせとして機能しない |
| メモの中で情報が食い違っている | どちらが正しいかは、作成者にしか分からない |
| 読み手が分からない | 住民向けと職員向けでは、言葉づかいが大きく変わる |

選択肢には「お知らせに書かない」を必ず含める。メモに書かれていないことには、「あえて書かない」場合もあるため（例：定員を設けない、費用は書かない）。

## 6. 使っている設計パターン

共通のパターンは [docs/prompt-patterns.md](../../../docs/prompt-patterns.md) を参照。

| パターン | このRecipeでの使い方 |
|---|---|
| P1 処理の順序を固定する | 把握 → 抽出 → 整理 → 確認 |
| P2 分類は定義で渡す | 項目（いつ・どこで・だれが・なにを・条件・問い合わせ先・変更）と、状態（記載あり・不足・矛盾）の定義（3章） |
| P3 禁止事項を具体的に書く | 日時・連絡先の補完、曜日の計算、食い違いの片方の採用、条件の省略 |
| P4 分からないことの書き方を決める | STEP 1は「不足」「矛盾」、STEP 3は【要確認：○○】 |
| P5 出力フォーマットを固定する | 項目の整理の表、お知らせ文（タイトル・本文・要点・問い合わせ先・件名） |
| P6 中間出力を次の入力にする | STEP 1の表を、STEP 3の唯一の根拠にする |
| P7 必要なときだけ質問する | 不足・矛盾・読み手に限定（5章）。「お知らせに書かない」の選択肢を含める |
| P8 確認対象を指定してセルフチェック | 作られた情報、抜け、条件、【要確認】、言葉づかい |
| P9 入力の区切りと念押し | メモを `↓↓↓` `↑↑↑` で囲み、メモの後で「推測で補わない」を再確認させる |
| P10 文字数の上限に備える | メモの欄が空のときは待つ指示。`page.md` に、分けて送る方法とメモを短くする方法を載せる |

## 7. 限界と注意点

- メモにない情報は作らないため、メモが少ないと【要確認】が多く残る。これは設計どおりの動作である
- 曜日の正しさは確認しない。日付と曜日の照合は人間が行う
- 組織の文書の様式（公印、文書番号、宛名の書き方など）には対応していない。必要な場合は、出力を組織の様式に貼り付けて使う
- 法令に基づく通知（期限を過ぎると不利益があるもの）は、内容の正確さに特に注意し、担当部署の確認を経て使う
- やさしい日本語や多言語への対応は、このRecipeの範囲外である

### テストケース

架空の団体・地名によるメモを使う。1〜6は [evals/](evals/) に作成済み。

| ケース | 内容 | 確かめること |
|---|---|---|
| 1. 標準 | 必要な情報がそろったメモ | 基本動作。情報を落とさず、作らないか |
| 2. 不足 | 申込締切と問い合わせ先がないメモ | 不足を質問し、答えがない項目を【要確認】で残せるか |
| 3. 条件が多い | 雨天時、先着順、年齢による条件があるメモ | 条件を落とさないか |
| 4. 変更 | 日程変更のメモ（変更前と変更後がある） | 変更前と変更後を取り違えないか |
| 5. 走り書き | 略語、重複、時刻の食い違いがあるメモ | 矛盾を質問できるか |
| 6. 職員向け | 社内向けのシステム停止のお知らせ | 読み手に合わせた言葉づかいになるか |

### 評価指標

[docs/evaluation.md](../../../docs/evaluation.md) の基本評価項目に加えて、次を記録する。

| 評価項目 | 確認内容 |
|---|---|
| 事実性 | メモと回答にない日時・場所・金額・連絡先・曜日を書いていないか |
| 網羅性 | メモにある、読み手に必要な情報を落としていないか |
| 条件の保持 | 雨天時・先着順・対象の条件・注意事項を残せたか |
| 不足・矛盾の扱い | 不足・矛盾を見つけて質問し、答えのない項目を【要確認】で残せたか |
| 読み手への適合 | 読み手に合った言葉づかいか。読み手が一度読んで行動できるか |
| 質問品質 | 必要な質問だけを、答えやすい形でしているか |
